# 学校级组织与管理员端 MVP（学校 + 教师）设计

## 范围与目标

本设计在 `feature/school-admin-mvp` 上交付学校级组织边界、唯一平台管理员、学校与教师管理、教师邀请码注册、教师资料和本校自主建班。它必须保持现有教师任务设计、发布、学生提交、反馈、评价和不可变历史的资源 ID 与快照内容不变。

本期明确不做学生自注册、学生学校级目录、Excel 导入、学生密码重置或管理员编辑学生资料。既有 rosterKey 名单码和学生教学流程保持 legacy 兼容。

## 数据模型与迁移

- 新增 `School`：不可变的公开 `code`、可编辑名称、`ACTIVE | DISABLED` 状态与仅存 SHA-256 哈希的教师邀请码。
- `AppUser` 新增可选 `schoolId`、工号/学号、教师主学科/兼教学科、账号状态和 `legacyProfile`。`ADMIN` 没有学校；新增教师必须具有学校、规范化工号和主学科。
- `Classroom.schoolId` 是必填字段。数据库触发器同时验证班级负责人为同校教师、成员为同校学生。
- 新增 `TeacherProvisioning`，用学校 + 工号作幂等键，持久化 Clerk 开通状态，但绝不持久化密码或邀请码明文。
- 迁移先独立加入 `ADMIN` 枚举值，再建表和约束。它创建固定 ID、代码 `LEGACY01` 的“历史迁移学校”，把既有用户和班级映射进去，标记为 legacy；不向活动、发布、提交、反馈、评价或快照表写入 `schoolId`。

学校代码使用 `SCH` 加不易混淆的随机大写字母/数字；创建后数据库触发器拒绝修改。邀请码使用至少 192 位随机值，只有建校或重置命令的单次结果含明文。

## 授权与隔离

`getCurrentActor` 是认证后的唯一状态门：账号必须为 `ACTIVE`，教师和学生还必须属于 `ACTIVE` 学校。页面布局不是授权边界；每个 Server Action、查询、命令和 Agent 路由仍以当前 actor 对资源所有权或学校归属进行检查。

管理员只能调用学校、教师和聚合数量的命令/查询，不能读取活动、学生作品、提交、反馈或评价。右下角 AI Agent 仍只在教师布局装载，管理员路径不装载它。

学校或教师停用只拒绝后续业务访问；不删除或改写历史记录。跨学校访问统一表现为不存在或无权限，避免泄露他校资源。

## Clerk 与开通补偿

Clerk 继续是唯一的密码保存和认证系统。教师看到的是“学校代码 + 工号 + 密码”；服务端根据不可变学校代码和规范化工号派生 Clerk 内部 username，用户不需要知道它。

教师注册按以下顺序执行：

1. 仅以邀请码哈希查找已启用学校，失败统一返回“邀请码无效或已失效”。
2. 在 PostgreSQL 创建或恢复 `PENDING` provisioning 记录，并检查同校工号唯一性。
3. 在数据库事务外调用 Clerk 创建 Username + Password 用户，使用 provisioning ID 作为外部幂等标识。
4. 再以可重试事务创建 `AppUser(TEACHER)` 并完成 provisioning。
5. 若 Clerk 已成功而数据库最终写入失败，重试会按外部标识找到同一 Clerk 用户并恢复；若邀请码/学校状态已改变导致不能完成，执行安全补偿并留下无密码的失败状态供重试。

管理员密码重置同样在事务外调用 Clerk，使用新生成的一次性随机密码并撤销旧会话；密码只出现在本次管理员确认结果，绝不进入数据库、审计、日志、Git 或浏览器持久化存储。

## 领域命令与查询

新命令均通过 `CommandContext` 接收已认证 actor，不让页面直接使用 Prisma：

- 管理员：创建学校、变更学校状态、重置教师邀请码、变更教师状态、重置教师密码；
- 教师：验证邀请码、注册、更新个人资料、创建本校班级；
- 查询：管理员概览、学校列表、教师列表、当前教师资料和教师班级列表；
- bootstrap：`pnpm admin:bootstrap -- <Clerk user ID> --confirm-database`，只绑定已有 Clerk 用户，不保存密码，也不覆盖教师/学生角色。

可重放的业务命令使用既有 `IdempotencyRecord` 与追加式 `ActionAudit` 模式；审计请求哈希只包含安全摘要，不能包含密码或邀请码明文。Clerk 或其他外部调用绝不放进 PostgreSQL 事务。

## 页面与体验

- `/admin`：学校、教师、学生、班级数量概览。
- `/admin/schools`：建校、名称编辑、启用/停用、人数计数和邀请码重置；学校代码只读。
- `/admin/teachers`：按学校筛选教师，查看主/兼教学科并启用、停用或重置密码。
- `/teacher/register`：邀请码验证成功后才显示学校名称，再收集工号、姓名、学科和密码。
- `/teacher/login`：学校代码、工号、密码的定制 Clerk Username + Password 登录。
- `/teacher/profile`：教师只能维护姓名与学科资料。
- `/teacher/classrooms`：当前教师创建本校班级；既有名单码成员页继续保留。

所有教师与管理员 UI 使用现有全局 token 和 Classical 视觉系统，不在组件内硬编码颜色、字体或间距。高影响的启停、邀请码重置和密码重置均使用明确确认对话框。

## 验收与风险

自动化验证至少覆盖：legacy 数据回填、同校唯一/跨校可复用工号、学校/教师停用、邀请码重置、教师注册的并发与补偿、管理员单例、班级及成员跨校约束，以及 v1/v2/v3 教学历史读取不变。

本地单元与数据库测试可以验证业务边界；真实 Clerk Development 实例还需要人工确认 Username + Password 已启用，以及注册、登录、会话撤销和可能的二次验证状态。该外部配置未完成前，不能声称真实 Clerk E2E 已通过。
